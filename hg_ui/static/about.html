A notebook that thinks about your notes,
without sending them anywhere.

You write the way you'd write on paper — messy, fast, unpunctuated. A local AI agent reads each note and quietly adds what makes it findable later: a title, tags, a summary, links to related notes, the tasks buried in the middle of a paragraph, and the dates that belong on your calendar.

What it does

For everyone

A note's journey

From the moment you hit Save to the moment it's part of your knowledge graph — a couple of minutes, entirely in the background.

Your note is usable the whole time — enrichment adds to it, never blocks it.

  1. You capture

    Type or dictate. The note is saved and readable immediately; nothing waits on the AI.

  2. The agent notices

    A background process watches the database over a live event stream and picks the note up in under a second.

  3. The model reads it

    A 2.6 GB language model runs on the phone, producing a title, summary, tags, tasks and reminders — and, if you've asked for it, a cleaner version of your text.

  4. It's linked and filed

    The note becomes a vector so it can be compared by meaning against everything else you've written. Related notes are linked both ways.

  5. It goes live

    No approval step — the note is simply better than it was. Your original stays in revision history, one tap away.

For everyone

What you control

The AI is a collaborator with clear limits — and every limit is yours to set, per note or globally.

Three levels of help

ModeWhat you getYour words
Fulltitle, tags, summary, tasks, reminders — and a rewriteRewritten · original kept
Metadatatitle, tags, summary, tasks, remindersUntouched
OffnothingUntouched

Set it while writing, from the capsule beside Save, or later from a note's ⋯ menu. The choice is per note and never sticky — one note set to Off doesn't quietly change every note after it.

Off takes effect immediately. Full and Metadata shape the next enrichment, so flipping them on a settled note changes nothing until something re-runs it. The menu says so rather than leaving you to wonder.

Nothing is a dead end

Every rewrite is reversible

The pre-polish text is archived as a revision. Restore is one tap, and the AI never overwrites a note you've hand-edited.

Dismissals are remembered

Reject a suggested task and it won't return on the next run — the agent keeps a record of what you turned down.

Your calendar stays yours

Events are only created from dates you wrote. Deleting a note cleans up the events it made; nothing else is touched.

Protected notes stay verbatim

Mark a note to keep your exact words and the agent will describe and tag it, but never reword it.

For everyone

Where your notes actually are

This is the part most note apps are vague about, so here it is precisely.

📵

No cloud, no account

There is no server to sign up for. Your notes live in a single SQLite file on your device.

🧠

The model is local

Gemma runs on the phone's own silicon. Enrichment works in airplane mode — that's the proof there's no round trip.

🚪

Remote access is RAM-only

Open the app from another device and nothing persists there. The local cache is deleted on a non-local origin, by design.

🗓️

Calendar is the one exception

If you enable it, event titles and times go to Google Calendar — because that is the point of a calendar. Nothing else leaves.

The single deliberate exception to "nothing on the client" is your light/dark preference. It carries no content, and saves you re-picking a theme on every visit.

For the technically curious

Under the hood

Two small processes, one database, no network dependency.

PieceWhat it is
InterfaceA Flask-served PWA — installable, offline-capable, no build step
AgentA Python daemon that watches the database and does the thinking
ModelGemma-4-E2B-it (2.6 GB) via LiteRT-LM, 32K context capability
StorageOne SQLite file — notes, enrichments, tags, tasks, reminders, revisions
SearchFTS5 keyword index + 384-dim MiniLM embeddings, hybrid ranked
RuntimeTermux on Android — no root, no special permissions

How the two processes talk

They don't, directly. The database is the interface. The UI writes a note; the agent notices and writes enrichment back. Either can be restarted, upgraded or killed without the other caring — and if the agent is off, the app is simply a fast notebook.

For latency, the UI publishes a server-sent events stream that the agent subscribes to, so changes are picked up in under a second rather than on a poll. A slow poll remains as a safety net; the stream is an optimisation, never a requirement.

Why on-device is slower, and still right

A cloud model would answer in two seconds. On a phone it's closer to ninety. What you get for the wait: notes that never leave the device, no account, no subscription, no rate limit, and an app that works on a plane. The agent is asynchronous precisely so that cost stays invisible — you've moved on by the time it finishes.

For architects

Architecture

A deliberately boring design: shared-nothing processes, a durable contract between them, and no component that can take the system down with it.

Two processes, one contract. Neither can corrupt the other's state, and either can be replaced independently.

Why the database is the interface

An HTTP API between the two would have been the obvious choice. It was rejected because it makes the agent a dependency of the app: when the daemon is down, restarting, or thermally throttled, a call fails and the user sees an error for something they never asked for.

With SQLite as the contract, the failure mode is latency, not error. A note written while the agent is off is simply enriched later. Recovery is automatic and needs no queue, no retry policy and no reconciliation logic — the database is already the queue.

Durability decisions worth naming

  • Deletions outlive their rowsCalendar events queued for removal live in their own table, not on the reminder. Deleting a note cascades its reminders away — if the queue lived there, the event would be orphaned in the calendar with nothing left that knew about it.
  • Retries are bounded and visibleA permanently failing calendar deletion stops after five attempts and records why, rather than retrying every minute forever against a revoked token.
  • Idempotency by key, not by luckThe deletion queue is keyed on the event id, so enqueueing twice is a no-op. Reminders dedupe on the resolved time slot, so a re-worded reminder can't become a second event.
  • Config self-correctsA stale hand-edited value that no longer fits the model's context is clamped at runtime and logged, rather than silently rewriting a truncated note.
  • The model is replaceableNothing above the engine layer knows which model is loaded. Swapping it is a path and a context size.
For the technically curious

The token budget

One constraint governs speed, note size and output quality — worth understanding before you tune anything.

An 80-word note is dwarfed by the instructions that accompany it — which is why a short note isn't instant.

Raising the context lets bigger notes through but slows down every note, including tiny ones, because the KV cache grows with it. 6,144 is the measured sweet spot on this hardware: roughly 2× faster than 32K with no practical loss, since almost no note needs more.

These values move together. Raise model_max_num_tokens and the polish word-limit re-clamps itself to match. The test suite fails if the three ever become incoherent.

For anyone who designs things

Design principles

The rules this app was argued into — usually after getting something wrong first.

  • Capture is sacredNothing may delay or complicate writing a note. Every AI decision happens after the fact, in the background. If you must configure something before you can type, the design has failed.
  • Your words are yoursThe AI describes freely and rewrites carefully. A rewrite is always reversible, never happens to a note you've hand-edited, and can be switched off per note.
  • A switch about the future must not rewrite the pastTurning AI off for a note stops the next run — it doesn't hide the title and tags you already had. An early version did, and stranded notes with nothing left to act on.
  • No action may be a dead endEvery state has an exit. Dismissals undo, rewrites restore, failures say what failed and what to do next.
  • Silence earns trustA daily "you have 0 things" teaches people to ignore a channel, and once ignored it's worthless. Say nothing when there's nothing.
  • Don't ask twiceDeleting a note already confirms intent — its calendar events go too, without a second prompt. Confirmation is for genuinely irreversible surprises, not for ceremony.
  • Optimistic, then honestA control moves the moment you press it, then reconciles with the server. Waiting for a round-trip feels broken even when it succeeds — but if it fails, say so and put it back.
  • Latency, not errorWhen a component is down the system slows; it does not break. This is the reason behind every architectural choice on this page.

A healthy note reads decision: suggest → generating (80 words, polish=y) → inference returned in … → adopted polished text as new body → auto-approved in QS.

Tuning

Configuration lives in ~/.quicksilver/config.quicksilver.json and is a sparse override — anything you omit uses a default that improves over time. Only override what you actually need; a pinned value freezes at whatever was right the day you wrote it.
